# 网关上游请求超时(504)告警处理方案

## 告警名称
API_GATEWAY_TIMEOUT

## 问题描述
客户端经 Nginx/API 网关访问服务时偶发或批量返回 504 Gateway Timeout，浏览器/接口表现是响应时间很长后超时，或页面长时间转圈。

## 排查步骤

### 步骤1: 获取当前时间
记录 504 集中出现的时间段，与上游应用的慢请求、慢查询时间对齐。

### 步骤2: 看网关日志
```bash
tail -f /var/log/nginx/error.log
```
搜索 `upstream timed out`、`504`，确认是哪个 upstream（哪个后端服务/IP:port）超时。

### 步骤3: 区分是上游慢还是网络/网关问题
- 看后端应用自身监控：该时段接口 P99 是否真的上涨（上游慢）。
- 看 TTFB（首字节时间）：网关收到响应慢 → 上游问题；TTFB 短但整体 504 → 可能是传输/响应体问题。
- ping / mtr 检查与上游之间的网络、丢包、连接复用。

### 步骤4: 检查网关超时配置
Nginx 里默认 `proxy_read_timeout 60s`、`proxy_connect_timeout 60s`。如果上游某些接口本身就慢于该值，会被网关主动掐断返回 504。

### 步骤5: 观察上游是否过载
并发打满、线程池满、慢查询堆积，都会让上游在超时时间内给不出响应。

## 常见原因分析

### 原因1: 上游应用处理超时
上游自身被慢SQL/线程阻塞拖慢，超过网关等待阈值。

### 原因2: 网关读超时配置过短
proxy_read_timeout / proxy_send_timeout 设得比上游合理耗时还小，长耗时接口被网关掐断。

### 原因3: 网络抖动或连接异常
到上游的网络丢包、连接未复用反复建连、TCP 重传。

### 原因4: 上游实例过载
单实例扛不住，请求在应用队列里排队超过超时时间。

## 处置建议
1. 先确认是全局还是个别上游/个别接口，缩小范围。
2. 对确有慢业务的上游，合理调大 proxy_read_timeout 或对长接口单独路由。
3. 根治上游慢问题（慢查询优化、扩容、限流），并让网关超时略大于上游合理 P99。
